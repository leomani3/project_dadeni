# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity **6000.3.9f1** (Unity 6), URP, new Input System.
This project is dedicated to building a roguelike deckbuilding game with tactical grid based combat. 


## Build / run / test

- Play mode entry: any scene works (see Bootstrap below). Scenes are `Assets/_GameAssets/Scenes/{InitScene, MenuScene, MainScene, CombatScene}.unity`, in that build order.
- `*.csproj` / `*.sln` at the repo root are Unity-generated. Never edit them; they are rewritten on asset import.
- There is no CLI build script and no lint config. Builds go through the editor.

### Fast feedback loop (use this before touching the editor)

**`Tools/CoreTests/` runs the `Dadeni.Core` tests headlessly in ~1 second, with Unity closed:**

```
cd Tools/CoreTests && dotnet run
```

It compiles `Assets/_GameAssets/Scripts/Core/**` plus `Assets/Tests/Dadeni.Core.Tests/**` into a console app and executes them with a small reflection runner over NUnit attributes (`HeadlessTestRunner.cs`). Pass a substring to filter: `dotnet run -- Pathfinder`.

It references two local DLLs — `UnityEngine.CoreModule.dll` from the installed editor and `nunit.framework.dll` from `Library/PackageCache` — so there is no NuGet restore. Both paths are properties at the top of the `.csproj` and the build fails with a clear message if either moves (a Unity upgrade or a package hash change). **The same test files also run inside Unity** as the `Dadeni.Core.Tests` EditMode assembly, so a test written once is covered both ways; keep them NUnit-only and free of `UnityEngine` runtime calls so both runners stay valid.

### Assemblies

- **`Dadeni.Core`** (`Assets/_GameAssets/Scripts/Core/`) — grid topology/pathfinding/line-of-sight/shapes, map generation, and the seeded random services. It references UnityEngine for `Vector2Int`/`Mathf` only: **no `MonoBehaviour`, `ScriptableObject`, `GameObject`, `Transform` or `Debug` may enter it**, because those need a live engine and would break the headless runner. It cannot reference `Assembly-CSharp` (asmdefs never can), so anything it needs must move in with it.
- **`Dadeni.Core.Tests`** (`Assets/Tests/Dadeni.Core.Tests/`) — EditMode, references `Dadeni.Core`.
- Everything else under `_GameAssets/` and `Team Square/` still compiles into `Assembly-CSharp`, and `Assets/Plugins/` into `Assembly-CSharp-firstpass`. Predefined assemblies automatically reference every asmdef, so game code sees `Dadeni.Core` with no wiring.

**New gameplay rules belong in `Dadeni.Core` behind a plain data interface, with the MonoBehaviour acting as an adapter.** `ArenaGrid` is the worked example: it implements `IGridTopology` over its `GridCell` dictionary and keeps its old `GridCell`-returning signatures, while the algorithms underneath are coordinate-only and testable.

### Driving the editor from an agent session

The `unityMCP` server (MCP for Unity) controls the running editor and is the intended way to verify work in the real game:

- `refresh_unity(compile="request")` then `read_console(types=["error"])` — compile and check, no editor focus needed.
- `run_tests(mode="EditMode", assembly_names=["Dadeni.Core.Tests"])` + `get_test_job(job_id, wait_timeout=60)`.
- `manage_editor(action="play"/"stop")` — **the real bootstrapper runs**, so the boot sequence is not an obstacle; do not try to bypass it.
- `manage_camera(action="screenshot", include_image=true)` — returns the frame inline. Captures land in `Captures/` (gitignored).
- `execute_code` — arbitrary C# in the editor, the escape hatch for anything else.

`Deckbuilder.EditorTools.DebugScenario` (`Assets/_GameAssets/Scripts/Editor/`) is the scripted way into a known state, because the menu buttons are `CustomButton`s and do not respond to `Button.onClick`:

- `DebugScenario.State()` — one line: play mode, loaded scenes, seed, run phase, room index/type, enemy count. **Poll this instead of sleeping**; scene loads and fades are async.
- `DebugScenario.StartRun(seed, characterId = null)` — boots a seeded run straight into room 0.
- `DebugScenario.ListCharacters()`.

Playing in the editor can mutate the checked-in `GameData.asset` (see GameData below) — check `git status` after a play-mode session.

## Architecture

### Bootstrap
`Utils/Bootstraper.cs` uses `[RuntimeInitializeOnLoadMethod(BeforeSceneLoad)]` on an `async Task`: from any scene other than `InitScene` it disables every GameObject, `await`s `LoadSceneAsync("InitScene")` (so the persistent managers exist before anything else loads), then loads `MenuScene` — or `MainScene` when `cheatSettings.noMenu`. Set `cheatSettings.disableBootStrapper` to work in an isolated scene.

`Bootstraper` only hands over to `GameFlow.Boot()`, which decides where the game starts, in this order: **the combat sandbox** (`CombatSandbox.Instance.BootStraightIntoCombat`, on by default — see below), then a run save to resume, then the hub.

### Three ScriptableObject singletons in `Assets/Team Square/Resources/`
`GameConfig`, `GameData`, `GameAssets` — each exposes `static Instance` backed by `Resources.Load<T>("<Name>")`. They are the global service locator for data (`CombatSandbox`, under Combat sandbox below, follows the same pattern from `Assets/_GameAssets/Resources/`):

- **GameConfig** — tuning + `cheatSettings` (`preventSave`, `startResetData`, `noFTUE`, `noCurrencyRequired`, `noMenu`, `disableBootStrapper`, `debugSeed`) and `uiSettings` (shared button hover/click tween values, and `shieldColor`: **the one blue used for anything about block/shield** — read it from there rather than hard-coding a blue). `EntityHUD` tints the health bar's red `Fill` with it and shows the shield icon (`Sprites/UI/Icon_Shield.png`, white fill so it takes the tint) while the entity has block. `debugSeed` forces every run onto one seed; leave it empty for a fresh random seed per run.
- **GameAssets** — Odin `[AssetList]`-populated asset arrays (currencies today).
- **GameData** — *the save file*. Persisted with Easy Save 3 (`ES3.Save("GameData", this)` / `ES3.LoadInto`) into the same ScriptableObject instance. Runtime-only fields and `Action`s must be marked `[ES3NonSerializable]`. Writes set `isDirty`; `SaveManager` flushes every 5s and on `OnApplicationQuit`. Because save data loads *into the asset*, playing in the editor mutates the checked-in `GameData.asset` — use `GameData.ResetGameData()` or `cheatSettings.startResetData` to get a clean state.

### MonoBehaviour singletons
Managers derive from MyBox `Singleton<T>`: `Instance` lazily does `FindObjectOfType` and **never auto-creates**, so every manager (`GameManager`, `UIManager`, `SoundManager`, `StatManager`, `EntityManager`, `TutorialManager`, `FadeManager`, `CameraManager`, `FloatingTextManager`, `FlyingParticleManager`, `SaveManager`) must live in a loaded scene. `InitializeSingleton(persistent)` is the opt-in for `DontDestroyOnLoad` + duplicate destruction.

### UI stack (4 layers, init cascades downward)
`UIManager` (registers every child `CanvasHandler` **by its concrete Type** in `Awake`, `GetCanvas<T>()`) → `CanvasHandler` (owns a `Canvas`, opens/closes its `UIContainer`s, disables the Canvas only after all containers finish closing; `GetContainer<T>()`) → `UIContainer` (DOTween fade/move in-out, `EnableByDefault`, `OnCloseComplete`) → `AUIElement` (`Init`/`Show`/`Hide`, base of `CustomButton`, currency widgets, …).

Consequences: one `CanvasHandler` subclass per canvas (a second instance of the same type is ignored with a warning), and `AUIElement.Init()` is driven by the container cascade, not only by `Start()`.

### Stat system (`Team Square/Stat System/`, namespace `Stats`)
`StatManager` owns every `Stat`, across two independent axes:
- **Entity axis** — keyed by `EntityType` (a `[Flags]` enum), seeded at `Awake` from `EntityStatDefinition` assets.
- **Source axis** — keyed by any `ScriptableObject` (card, ability, item), each holding a `Stat[MAX_STEPS, MAX_APPLICATIONS]` grid addressed by `(step, application)`. This is the generalized form of the source project's ability stats; nothing in the framework names a concrete source type.

Each axis has a **definition** tier (persistent, what meta-progression modifies) and an **instance** tier (per spawned GameObject). Instance stats subscribe to their definition `Stat.OnValueChanged`, so a definition upgrade propagates live to everything already spawned. `EntityStatModule` registers/unregisters the entity automatically; `UnregisterInstance` unsubscribes both axes — skipping it leaks into the definition's event.

`StatModifier` carries either an `entityType` or a `statSource` + `step`/`application`; the single-argument `AddDefinitionModifier(mod)` / `RemoveDefinitionModifier(mod)` route to the right axis. An entity-axis modifier applies to *every flag* in the mask via `EntityTypeExtensions.GetFlags()`.

`Stat` caches lazily and computes `flat * (1 + addedPercent / 100) * multiplier` — **`ModifierType.Percentage` values are whole percents (25 = +25%)**, not fractions. Modifiers with a non-null `id` are *replaced* rather than stacked; `AddModifier` stores a `Copy()`.

`StatType` uses explicit numbering with gaps, because its values are serialized inside `EntityStatDefinition` assets and modifiers — add entries, never renumber.

### Entity system (`Team Square/Entity System/`)
`Entity` is the composition root: it holds the `EntityType`, discovers its `EntityModule` components and drives their lifecycle — `Initialize`/`OnInitialize` per module → `OnAllModuleInitialized` once all exist → `Cleanup` on despawn. Modules find each other through `Entity.TryGetModule<T>()` rather than direct references, and the module dictionary is keyed by every type in the inheritance chain, so `TryGetModule<EntityHealthModule>()` also finds a subclass.

`Entity` implements LeanPool's `IPoolable`: `OnSpawn` initializes modules and registers with `EntityManager`; `OnDespawn` cleans them up. `EntityManager` is the runtime registry (all entities, enemies, entity-by-collider) — nothing needs a scene search. The player is owned by `RunManager`, not the registry. `Entity.OnDestroy` unregisters too, because scene unloads destroy entities without despawning them.

Shipped modules: `EntityStatModule` (instance stats), `EntityHealthModule` (health/damage/death, MaxHealth read from the stats), `EntityTeamModule` (`Team.Player`/`Team.Enemy`, drives EntityManager bucketing), `EntitySpawnModule` (spawn animation + VFX window), `EntitySheenModule` (white emission flash on hit). Game-specific reactions belong in listeners of `EntityHealthModule`'s events or in a subclass overriding `PlayDamageFeedback` / `Die`.

### Animation (`_GameAssets/Scripts/Animation/`, `EntityAnimationModule`)

**A character's animations are one asset: a `CharacterAnimationSet`.** It holds Idle, Run, Death and a `CastStyle` → `AnimationMove` table, and may name a **parent set**: any clip or move left empty is read from the parent chain. **Speeds are per character and never inherited or shared**: `m_idleSpeed` / `m_runSpeed` / `m_deathSpeed` and each cast row's `speed` are read from the character's *own* set only, whichever set supplies the clip or move. A cast row may therefore hold a speed with no move — it keeps the inherited move and only retimes it for this character (`AnimSet_Ranger` plays the default set's `Move_MagicRaise` at ×4 this way). A cast speed belongs to the style actually played, so a `HeavyAttack` card falling back to `Attack` uses the `Attack` row's speed. `AnimSet_Humanoid_Default` covers every KayKit Rig_Medium character (the clips are Humanoid, so they retarget between Adventurers and Skeletons), and `AnimSet_Ranger` / `AnimSet_Skeleton` only list what differs. Sets live in `_GameAssets/Animations/Sets`, moves in `.../Moves`, and clips we authored ourselves in `.../Clips` — **never edit or add files under `Assets/KayKit/`**, so the pack can be updated.

**An `AnimationMove` is a clip plus its timing**: `m_impactTime` (normalized 0–1, the moment the card's effects apply). It is shared by every character that uses it, which is why it carries no speed. The timing lives on the move, not in the clip, so **clips carry no animation events** and any clip — KayKit `.anim` or a clip inside an FBX — is used as-is, with no duplicating. `Deckbuilder/Animation/Validate` reports a clip that still carries events, since nothing receives them anymore.

**Cards choose a `CastStyle`, never a clip.** `Default` means the card type's base style (`Attack` for Attack cards, `Utility` otherwise); any other style (e.g. `HeavyAttack`) is looked up in the caster's set and falls back to the base style when the set chain has no move for it. So one card animates differently per character, and a special card gets its own look by picking a style and giving the characters that need it a move for that style. `CastStyle` uses explicit numbering — append, never renumber.

**`EntityAnimationModule` owns the Animator.** Its `m_controller` (`Entity.controller`) is set once on the `Player` / `Enemy` base prefabs and its `m_animator` is auto-found under the model (`Reset`/`OnValidate`), so a new character only needs its set assigned. At runtime it builds an `AnimatorOverrideController` from the set, mapping the controller's placeholder clips (`IdlePlaceholder`, `RunPlaceholder`, `CastAttackPlaceholder`, `CastUtilityPlaceholder`, `DeathPlaceholder`) by name — renaming one throws at init. There are no `.overrideController` assets and the Animator component on the model has no controller assigned. `PlayCast` waits for Locomotion, swaps the cast placeholder for the move's clip, sets the `CastSpeed` parameter, fires the trigger and applies the card when the state passes the impact time; `PlayDeath` sets `DeathSpeed`, plays the `Death` state and waits the clip's length divided by that speed. Each frame `LocomotionSpeed` (the Locomotion state's speed multiplier) is lerped from the idle speed to the run speed by the damped `Speed` blend value, so each end of the blend tree plays at its own speed.

**A move also decides how the card's effects reach their targets** (`m_delivery`, an `ImpactDelivery`), because that is presentation: it never changes what is applied to whom, only how it looks. Card effects run in two phases. At the move's impact time — the *release* — `CardExecutor.TryResolve` freezes the target cell and the entities in the effect zone, and every `targets=Self` action applies at once (`CardAction.ApplyToCaster`). The rest, the *arrival* phase, depends on the delivery:

- `Instant` — arrival happens at the release too (melee, self buffs).
- `ProjectileToTargetCell` — one projectile flies to the target cell's ground point and its landing applies everything to the whole zone (an explosive arrow).
- `ProjectileToEachTarget` — one projectile per entity some action affects (`CardAction.Affects`), each aimed at that entity's `HitPoint` and applying the card to that entity alone (a volley); cell-level actions such as `SummonCardAction` apply when the last one lands. With no affected entity it falls back to one projectile at the cell, so shooting at nothing still shows a shot.

So the shape of a special card's presentation is chosen the usual way: the card picks a `CastStyle`, and the caster's move for that style carries the clip *and* the delivery. The Ranger's `Move_BowShot` is `ProjectileToEachTarget` with `Projectile_Arrow`, so the base Attack shoots one arrow and the upgraded one (Cross zone) shoots one per target. A `CardAction` subclass implements whichever of `ApplyToCaster` / `ApplyToTargetCell` / `Affects` + `ApplyToEntity` fits; `EntityCardAction` routes its `targets` field onto them.

`PlayCardAction` keeps the action running until every projectile has landed, so the action queue (and a queued end turn) waits for arrivals, not just for the clip. `EntityAnimationModule` carries the two anchors: `CastOrigin` (where projectiles leave; on the `Player` / `Enemy` base prefabs at chest height in front of the model — point a variant at a hand or bow bone to refine it) and `HitPoint` (where projectiles aim on a target).

**`Projectile`** (`Combat/Projectile.cs`) is the root of a projectile prefab in `_GameAssets/Prefabs/Projectiles`: it is pooled with LeanPool, flies at `m_speed` along a shallow arc (`m_arcHeightPerUnit` of the distance), faces along its velocity, spawns the optional launch and impact VFX (pooled, despawned after `m_vfxLifetime`; the impact VFX's up axis is the surface normal — horizontal toward the shooter for an entity, world up for a cell), then stops its particles and despawns once its trails have faded. `m_flightParticles` and `m_trails` are filled by `Reset`. The art under it is a vendor effect stripped of its scripts, rigidbody, collider and per-particle lights (`VFX_Arrow01_Orange_*`, from Gabriel Aguiar's Unique Projectiles Vol 3, with its materials/textures/shaders under `Assets/GabrielAguiarProductions` at their vendor paths and GUIDs); vendor `TrailRenderer`s ship with `autodestruct` on, which must be turned off or a pooled projectile destroys itself.

**`Deckbuilder/Animation Lab`** (`Editor/AnimationLabWindow.cs`) is where animation work happens: pick a character, pick a slot, and the model plays in the window (drag orbits, wheel zooms, Space plays, ←/→ steps a frame). Cast slots show the impact marker on the timeline, draggable and frame-snapped. Every slot has a `Speed (<own set>)` field that writes only the selected character's set, so it can never affect another character; preview playback and the "plays in" duration follow it, and the slot list shows any speed other than 1 as `×1.25`. The move fields below it (clip, impact, delivery) edit the shared move, and the window says so. Assigning a clip or move in the window writes it into the **selected character's own set**, overriding whatever it inherited; inherited slots are greyed with an ↑. The Cards list shows which move each card resolves to for that character and edits each card's style. Ctrl+S saves. From an agent session, `AnimationLabWindow.Validate()` returns the problem list.

### Camera
The rig is split in two. **One persistent `CameraManager.prefab`** (InitScene) carries everything there can only be one of — the real `Camera`, the `CinemachineBrain`, the URP data, the `Volume`, the `AudioListener` and the `PhysicsRaycaster`. **Each scene that needs a view ships its own `CameraRig`**: a `CinemachineCamera` (`CinemachinePositionComposer`, no Aim) plus the `FocusAnchor` transform it tracks. MenuScene, MainScene and CombatScene each have one; the persistent half is never duplicated into a scene, so only the framing is per-scene.

**Newest-wins is Cinemachine's job, not ours.** A vcam registers with `CinemachineCore` on enable and the brain drives the highest-priority live one, so CombatScene's vcam (`Priority` 10, the only one with priority enabled) takes over the instant that scene loads additively over MainScene, and when it unloads the brain falls back to MainScene's vcam by itself. There is no handover code, no singleton juggling, and never a second `Camera` or `AudioListener`. The brain's `DefaultBlend` is **Cut**, so context changes are instant as they always were — set a blend time there and every scene transition gets one for free.

**The framing is authored per scene, never set from code**, so opening the scene you are working in shows exactly what the game will look like there, and a change in one scene no longer touches the others. All three hold the same values today: the `Camera`'s own Projection dropdown says Orthographic (the single source of the mode — the brain's `LensModeOverride` is deliberately off so nothing overrides it), the vcam's lens holds `Orthographic Size` 12 (the only framing knob — half the visible height in world units), the vcam's transform holds the angle as a plain rotation (pitch 55, yaw 45 — matched to the `EditorPreviewCamera` authored in CombatScene, which is what the arena was framed against; it is not the `atan(1/√2)` = 35.264 true isometric angle, so the three world axes are not 120° apart on screen), the composer's `Composition.ScreenPosition` (-0.0264, 0.1584) puts the focus point left of and below screen centre rather than dead centre (also taken from that preview camera, which is hand-placed off its parent's axis — note its y is inverted relative to `WorldToViewportPoint`, and its x only holds at 16:9 since it is normalised against the width), and the composer's `Camera Distance` 50 is how far back the camera parks (in orthographic it changes nothing about the framing, only what gets clipped in front and how far shadows must reach).

To judge a shot without play mode, the vcam's frustum gizmo (`ShowCameraFrustum` is on) is enough in the Scene view; for a real game-view preview load `InitScene` additively first, since the only `Camera` and the brain live there, then use the vcam's **Solo** button.

The view never changes at runtime: **the camera has no input of any kind** — no zoom, no rotation, no pan. The scroll wheel and the mouse buttons are free for gameplay. `CameraManager` therefore has no control-gating API; when camera input comes back it brings its own.

All `CameraManager` does is move **the anchor the live vcam tracks**, read each `LateUpdate` off `_brain.ActiveVirtualCamera.Follow` — so it needs no registration call and holds no reference into any scene. It `SmoothDamp`s that anchor onto the current focus target (`_focusSmoothTime`, capped by `_maxFocusSpeed`, which keeps long context jumps from whipping), and the composer keeps the camera `Camera Distance` back along its own forward from it. When the live anchor changes, because another scene's vcam took over, the anchor is **snapped** to the focus target rather than travelling to it, so loading a scene never drags its camera across the map.

- `FocusOn(point)` — a fixed shot, used by the menu (`HubManager._menuFocusPoint`) and combat (`CombatManager.m_cameraFocusPoint`, wired to CombatScene's own `FocusAnchor`, so the authored shot is also the target and the anchor stays where it was placed).
- `FollowTarget(target)` — the player, used by hub free-roam and the whole run.

Both do the same thing today (track that transform); the names exist so call sites say which they mean, and the difference is only whether the transform moves.

**Every scene that loads must set its own focus**, because the focus target survives a scene change while the anchor does not: `CombatManager.Start` covers combat and the sandbox, `HubManager.OpenMenu` / `EnterFreeRoam` the hub, `RunManager.LoadRun` / `ReturnFromCombat` the run. This is what replaced the old `CameraFocusPoint` marker.

**`Camera Distance` and the pipeline's shadow distance are coupled**, because URP measures shadow distance from the camera, not from what you are looking at. At pitch 55 one unit of on-screen height is `1/tan(55)` = 0.700 units of view depth, so an `Orthographic Size` of 12 spreads the visible ground over ±8.4 units of depth around the focus point: with `Camera Distance` 50 the ground runs from depth 42 to 58, and `m_ShadowDistance` in `Assets/Settings/PC_RPAsset.asset` is 80 to cover it with room to spare (a shallower pitch spreads that band wider — at the old 35.264 it ran 33 to 67 — so flattening the angle is what eats the headroom). Shrink it and shadows vanish from the back of the arena first. Since the pitch is now per-scene, that one number has to cover the shallowest vcam in the project. That asset is also down to **one shadow cascade**: the camera never changes distance, so every shadow caster sits in one narrow depth band far from the camera, where extra cascades only put a visible quality seam across the arena (the gameplay band gets ~22 texels/unit on one cascade against ~17 on the last of four). The dead 42 units in front of the view are the price of parking the camera that far back; raising the vcam lens's near clip would recover them, at the risk of slicing tall geometry.

A scene opened on its own still renders nothing in play mode, because the only `Camera` lives on the persistent prefab — that is what the bootstrapper is for, and `CombatSandbox` is the way to boot straight into combat.

### Run lifecycle
`GameManager.StartRun()` / `ResetRun()`: fade → `LeanPool.DespawnAll()` + despawn tutorials → deplete `gameSettings.resetedCurrency` → `GameData.ResetRun()`. `OnRunStart` / `OnRunEnd` are the hooks for game code. `GameManager` is `partial`, so run logic specific to the deckbuilder belongs in a second file under `_GameAssets/Scripts/`.

`RunManager` (persistent, InitScene) owns the deckbuilder run; the player entity itself belongs to `GameFlow`, which spawns it under itself so it survives scene loads. **`GameFlow` owns combat entry and exit**, because combat can be reached from a run or from the sandbox: `GameFlow.CombatEnemyPrefabs` is the enemy list `CombatManager.Start` reads (together with `GameFlow.Player`), and `GameFlow.EndCombat()` is what `CombatManager.EndCombat` calls — it routes to `RunManager.ReturnFromCombat()` during a run and to `RestartSandboxCombat()` in the sandbox. `RunManager.StartCombat(enemyPrefabs)` fills that list and the player's pose, deactivates every active MainScene root and **additively** loads `CombatScene`; `CombatManager.Start` makes its own scene active (so pooled combat spawns land in CombatScene and die with it), spawns the enemies on the grid and places the player. `RunManager.ReturnFromCombat` unloads `CombatScene`, reactivates MainScene's roots, restores the player pose and only then calls `Player.OnCombatExit()` (the NavMeshAgent warp needs MainScene's `NavMeshSurface` re-enabled). MainScene state — the current room included — survives combat. The camera needs no hand-restoring: CombatScene's `CameraFocusPoint` parks the focus anchor on the authored arena point, and `ReturnFromCombat` calls `FollowTarget(Player.transform)` to hand the view back to the player.

`GameFlow.IsInGameplay` (`Run` or `SandboxCombat`) is what `RunCanvas` and `EntityHUDModule` gate on, so the HUDs and the run canvas work in both. `RunCanvas` hides its complete-room button outside `Run`, since it drives `RunManager.CurrentRoom`.

### Combat sandbox (`_GameAssets/Scripts/Combat/CombatSandbox.cs`)
`CombatSandbox` is a fourth `Resources` singleton (`Assets/_GameAssets/Resources/CombatSandbox.asset`) and **the way to work on combat**: with `_bootStraightIntoCombat` on, pressing Play loads `CombatScene` directly — no menu, no hub, no map, no save — with the enemies the asset lists and **the starting deck of the character it points at**. Edit the asset to change the fight: `_character`, `_seed` (empty for a fresh seed each boot) and `_enemies` (Entity prefab + count), plus an Odin button for `SetEnemiesToSinglePrefab`. The sandbox holds no deck of its own — `BuildDeck()` expands `_character.StartingDeck`, so the deck you fight with is always the one authored on the `CharacterConfig`, and changing the loadout means editing that asset. Clearing the flag restores the normal save/hub boot.

In the sandbox the deck comes from the asset rather than `RunState`, so `GameFlow` loads it into `PlayerDeckModule` and refills health itself. **Ending combat restarts it** (fade → `LeanPool.DespawnAll()` → respawn the player → reload `CombatScene`) instead of returning to a room, which is the iteration loop. From an agent session `DebugScenario.Sandbox()` prints the loadout, `DebugScenario.StartSandboxCombat()` restarts the fight, and `DebugScenario.State()` now also reports the flow state, combat phase, active entity, living enemies and the hand/draw/discard counts.

### Arena layouts and the Arena Editor

**The arena is data.** `ArenaLayout` (`_GameAssets/Scripts/Grid/ArenaLayout.cs`) is a ScriptableObject holding a `cellSize`, an `areaSize` in world units and one `{ coordinate, CellType }` entry per cell — a coordinate absent from the list is *no cell*, a hole in the arena. It implements `IGridTopology`, so `GridPathfinder` and `GridLineOfSight` can run straight against a layout asset in a test, with no scene and no `GameObject`. Shipped layouts live in `Assets/_GameAssets/Objects/Arenas/`; `Arena_Default.asset` is the 9x9 arena the game ships with.

**`ArenaGrid` builds its cells from that asset and nothing else.** `Build()` clears `CellsRoot`, instantiates one `Cell.prefab` per entry at `coordinate * cellSize`, applies the `CellType`, and only then does the coordinate indexing, neighbour wiring and continuity check. `m_layout` and `m_cellPrefab` are `[Required]`: there is no hand-placed-cell path and no spacing measurement any more, so a missing layout throws rather than silently producing an empty grid. Changing `cellSize` on the asset is the one knob for arena scale.

**Each spawned cell is scaled by `cellSize / m_cellPrefabFootprint`, so tiles always touch.** `Cell.prefab` is authored one unit across, which is what `m_cellPrefabFootprint` records; spacing cells at `cellSize` without scaling them is what used to leave a `cellSize - 1` gap between every tile. Change that field only if the prefab's art stops being one unit wide. If you ever want visible grout between tiles, shrink the `Model` child inside `Cell.prefab` rather than breaking the scale relationship here — the cell's footprint has to stay equal to `cellSize` or the collider no longer matches the coordinate it answers for.

At runtime the old children are **detached before `Destroy`**, because `Destroy` only takes effect at end of frame and the `GetComponentsInChildren` that follows in the same call would otherwise see both generations and report every coordinate as a duplicate. In the editor the same method uses `DestroyImmediate` and `PrefabUtility.InstantiatePrefab`, so the cells stay real prefab instances.

`ArenaGrid` carries a `RebuildFromLayout` Odin button. Open `Arena.prefab`, press it, and the prefab's `_Cells` are regenerated from the asset — that is how the arena stays visible in the scene view while remaining data-driven.

**`Deckbuilder/Arena Editor`** (`_GameAssets/Scripts/Editor/ArenaEditorWindow.cs`) is the authoring tool: a standalone `EditorWindow` that needs no scene open. It draws the lattice with **the game camera's own projection** — yaw 45, pitch 55, so a cell is `1/sin(55)` = 1.22 times wider than it is tall — which means what you paint is framed exactly as the camera will frame it, not as a generic 2:1 isometric grid. Left mouse paints, right mouse erases, middle or Alt drag pans, the wheel zooms about the cursor, and the number keys pick a brush, all on the left of the keyboard: `1` erases and `2..n+1` are the `CellType` values, so nothing is bound to `0`. There is no hover highlight — the footer reports the coordinate under the cursor instead.

The brush palette is generated from `Enum.GetValues(typeof(CellType))` and `GetCellColor` falls back to a hue derived from the enum value, so **adding a `CellType` needs no edit to the window** — the brush, its hotkey and a colour appear on their own. Every edit goes through `Undo.RecordObject`, so Ctrl+Z works, **Ctrl+S saves the layout asset** (same as the toolbar's Save, with a notification), and the footer warns while either side has no spawn cell.

**The arena is sized in world units, and that size is the arena's boundary.** `m_areaSize` lives on the layout asset, not in the window, because it defines the arena rather than the view: `GetAreaCellCount()` is `floor(areaSize / cellSize)` per axis (with an epsilon, so an exact multiple does not fall a cell short) and `GetAreaBounds()` centres that count on the origin, which is the single source of truth for what exists. The window draws the lattice **only inside that rect**, brightens its border, and refuses to paint outside it; `IsInsideArea` gates both the hover readout and `PaintHovered`.

Editing the Area X/Z fields is a `DelayedFloatField`, so it applies on Enter rather than on every keystroke, and it immediately crops cells that fall outside the new rect — the data can never contradict the drawn grid. `Fill area` fills every coordinate in the rect, **keeping the type of each cell that already falls inside**, so changing `cellSize` and pressing it re-grids the same physical footprint with obstacles and spawns intact. Because the rect is always centred on the origin, a layout's cells are centred too; a hand-made layout that is not will be cropped the first time the area changes. New layouts default to `Assets/_GameAssets/Objects/Arenas`, beside `Arena_Default`.

### Run randomness (`_GameAssets/Scripts/Run/`)
**Every gameplay-affecting random draw must go through `RunRandom`.** A run is defined by a single seed, so a player can share a seed string and another player gets the identical run.

`RunRandom` is a static, seed-owning service: `Initialize(seed)` at run start, then `GetStream(RandomChannel.X)` anywhere. `RandomChannel` (`Map`, `Encounter`, `CardReward`, `Treasure`, `Shop`, `Event`, `Combat`) splits the seed into **one independent `RandomStream` per domain**, derived via `RandomStream.Mix(seed, channel)`. The channels exist so that consuming a draw in one system never shifts another system's sequence — add a die roll to shop pricing and the map for a given seed stays byte-identical. Adding a channel is free; reordering or renumbering `RandomChannel` invalidates every existing seed.

`RandomStream` (`Team Square/Utils/`) is a SplitMix64 generator — deliberately *not* `System.Random` or `UnityEngine.Random`, whose sequences are not guaranteed stable across platforms and engine versions, which would break seed sharing. It exposes `Value`, `Range`, `Chance`, `Pick`, `Shuffle`. `RunRandom.GetStream` throws if called before `Initialize`, and its statics are cleared on `SubsystemRegistration`.

Seeds are base-34 strings (`0-9A-Z` minus `I` and `O`, the two that read as `1` and `0` — `S` *is* in the alphabet); `ParseSeed` falls back to hashing so any typed word is a valid seed. Seed precedence in `RunManager.StartRun(seed)`: explicit argument → `GameConfig.cheatSettings.debugSeed` → fresh random seed.

`Utils/CusRandom` and raw `UnityEngine.Random` remain acceptable **only for cosmetic, non-reproducible effects** — VFX jitter, floating-text offsets, spawn rotation, audio pitch. Anything a player could replay or a bug report could reference belongs on a channel.

`GridPathfinder` no longer reaches for a stream itself: `TryFindPath` takes an optional `RandomStream`, where `null` means the deterministic exploration order. `ArenaGrid.FindPath` passes `RunRandom.GetStream(RandomChannel.Combat)` when its `_randomize` flag is set, so the decision now lives at the call site and the algorithm stays testable. Prefer that shape — an injected stream, never a static lookup — for any new Core code.

### Rooms and map
`MapData` is a branching Slay-the-Spire-style graph produced by `MapGenerator` (`_GameAssets/Scripts/Map/`) from a `MapGenerationSettings` serialized on `RunManager` and the `RandomChannel.Map` stream. Nodes are a `width * floorCount` grid plus one boss node, flat-indexed `floor * width + x`, so a room is still addressed by a single `int`. Because an edge only ever spans one column, the sign of `dx` maps exactly onto `DoorDirection` (Left/Straight/Right) — that is how the graph stays behind the two original topology calls, `GetNextRoomDirections(index)` and `TryGetNextRoomIndex(index, direction)`. Generation order is paths → trim converging first-floor edges → assign room types from a ratio bucket under the placement rules → connect the boss (last, so it never affects the bucket maths or the placement rules). `pathCount` is a number of path-drawing *iterations*, not visible branches: iterations share starting columns and merge as they climb, so 6 iterations yield ~3.4 entry points. `MapData.ToDebugString()` renders the graph as ASCII; `RunManager` writes it to `Logs/Map.txt` (editor) or `<persistentDataPath>/Logs/Map.txt` (build) on every run, because Unity's console font is proportional and mangles the alignment. `RunManager` maps `RoomType` → `Room` prefab (one `RoomBase` variant per type) and only ever has one room instantiated, in MainScene at the world origin, walking on MainScene's baked NavMesh. `SpawnRoom` destroys the current room, instantiates the next, enables the doors matching the next directions and warps the player to `Room.SpawnPoint`. A `Door` (`DoorDirection`, trigger collider + kinematic Rigidbody) locked until `Room.Complete()` calls `RunManager.EnterNextRoom(direction)` once the player stays inside it for `_enterDuration`, which fades to black and spawns the next room. `RunCanvas`'s complete-room button is a mock of the real completion condition.

### Cards and piles (`_GameAssets/Scripts/Cards/`)
`CardConfig` (SO) is the design data: `CardType` (Attack/Skill/Power), and a base and an upgraded block each holding cost, exhaust flag, target/effect `ZoneDefinition`, line of sight and a `[SerializeReference] List<CardAction>`, read through `GetX(bool upgraded)`. The asset splits cleanly into **rules** (cost/exhaust/zones/LOS/actions) and **presentation** (`m_illustration`, `m_castStyle`); keep that split, because the rules half is meant to be machine-readable.

### The card table (`Content/Cards.txt`)

`Assets/_GameAssets/Scripts/Editor/CardTable.cs` moves the rules half of every `CardConfig` between the assets and one readable text file. Menu items live under `Deckbuilder/Cards/`; from an agent session call `CardTable.Export()` / `CardTable.Import(dryRun)` through `execute_code`.

- **`Export()`** writes every card to `Content/Cards.txt` (LF endings, so edits from any tool diff cleanly).
- **`Import(true)`** parses, validates and reports which cards *would* change, touching nothing.
- **`Import(false)`** applies, then `SaveAssets`.

**Editing that file and importing is the intended way to do a balance pass or add content in bulk** — it is far faster than one inspector per card and the diff is reviewable. The project currently ships two cards, `card.attack` and `card.block` (`Objects/Cards/`), which make up the Ranger's starting deck.

Rules of the format:

- Export and import share one formatter, so **export → import → export is byte-identical**. If a round trip ever changes the file, that is a bug in `CardTable`, not in the data.
- Only cards whose rendered text differs are written, so untouched assets keep their timestamps.
- It carries **rules only**, plus one presentation field: `cast`, the card's `CastStyle`, because it is an enum that reads well in a balance pass. `m_illustration` and `m_id` are never written.
- **Import never creates or deletes assets.** An id in the file with no asset is an error; an asset missing from the file is an error. Add the `CardConfig` in Unity first, then export.
- **Any error aborts the whole import** and writes nothing, so a bad balance pass cannot half-apply. Messages carry the line number and card, e.g. `line 37 (card.block/base): GainBlockCardAction has no field 'blok'. Known fields: targetTeams, block.`
- Fields are discovered by reflection **up the whole inheritance chain**, so a private `[SerializeField]` on a base class (`EntityCardAction.m_targetTeams`) is included. A new `CardAction` subclass needs no work here — it appears automatically.
- Asset references (`StatusEffectConfig`, `Entity` prefabs) are written by **asset name** and resolved by exact name match; two assets with one name is an error telling you to rename.
- `Team` is a bit-combination enum without `[Flags]`, so values render as `Ally|Enemy`. The formatter decomposes any bit enum this way.
- Rewriting a card regenerates the `rid` values of its `[SerializeReference]` actions. That is harmless churn in the `.asset` diff and only happens for cards that actually changed. `CardInstance` is one physical card (config + upgraded state); everything at runtime — piles, execution, views — holds instances, so two copies of Attack stay distinguishable. The run's deck lives on the player as `PlayerDeckModule` (starting entries serialized on `Player.prefab`, rebuilt on `OnInitialize`). `CardPile` is an ordered list, index 0 = top, with add/take at top, bottom, any index or the first match of a predicate, plus `onCardAdded`/`onCardRemoved`/`onOrderChanged`. `CombatDeck` (serialized on `CombatManager`) owns the four combat piles: `StartCombat` shuffles the deck into Draw on `RandomChannel.Combat`, `TryDraw` reshuffles Discard into Draw when Draw is empty and sends overflow past the max hand size to Discard, `Play` moves a hand card to Exhaust or Discard. `CardPile` events carry the pile that fired them.

`CombatDeckView` (on `CombatCanvas`, bound by `CombatManager`) is the only view of the piles. It listens to all four piles: a removal records the source pile, the matching addition (always synchronous, same call) turns into a flight — a hand card's existing view flies to the destination anchor, any other transfer spawns a temporary pooled `Card` at the source anchor; flights are staggered through `ScheduleTransfer`, so the model changes instantly and the view catches up. Draws are "arrivals" driven by `UpdateArrivals`, not a tween: the card takes its hand slot (and the settled cards make room) the moment it is queued, waits face up at scale 0 on the draw pile until its staggered start, then every frame lerps from its start pose to a smoothed copy of its live slot pose, so slot changes mid-flight (hover, further draws) bend the path instead of snapping. Everything heading to a pile uses `Card.FlyAlongArcTo`: a quadratic Bézier rising `_arcHeightRatio × distance` above the higher endpoint, the card's top following the tangent, shrinking to `_pileCardScale` over the first `_shrinkPortionOfFlight` and flipping to the back (the `Card` prefab has `FlipPivot` → `CardVisual` front / `CardBack` back, toggled by `SetFaceUp` mid-squash) over the first `_flipPortionOfFlight`; a pooled `CardTrail` (a `MaskableGraphic` ribbon rebuilt each frame from the card's recent positions, tapering and fading over `_lifetime`, self-despawning once its target stops and its points expire) follows it. Cards flying to a pile, and their trails, are reparented to `FlightLayer`, a sibling of the `Hand` container with the identical rect (so local coordinates match) placed first under `Content`, so they draw behind the pile widgets, buttons and hand. Draws are the exception: they stay in `Hand`, kept as the last siblings while flying, so they never pop from behind to in front on landing. Combat cards are always initialized with `Card.Initialize(card, false)`: upgraded cards show their upgraded values and the `+` title without green highlighting, which is reserved for the rest-site upgrade preview. Hotkey labels are off unless `_showHotkeyLabels` is set; the number keys work either way. `EntityHUD`s live on the persistent `RunCanvas`, so `EntityHUDModule` hides its HUD in `OnDisable` (e.g. MainScene's roots deactivated during combat) and shows it again in `OnEnable`. Arriving cards count in the layout but are excluded from hover, press and hotkeys until they land. **Ending the turn is a queued action**: `CombatManager.EndPlayerTurn` sets `IsEndTurnQueued`, locks the deck view (which also drops the playable outline), greys out the End Turn button and enqueues an `EndTurnAction` on the player's `EntityActionQueueModule`; `PlayerActionController` ignores all input while it is set. The player's already-queued actions finish first, then `PassPlayerTurn` waits for `IsTransferring` to clear before switching to the enemy turn. A view removed from the hand and claimed by no pile by `LateUpdate` shrinks away. It also fans the hand, handles hover (straighten, rise, push neighbours), press-to-drag and click-to-follow (a release with the pointer moved ≤ `_clickMaxDistance` keeps the card following the cursor without the button held, until any press cancels it), either of which selects the card once the pointer passes `_selectionScreenHeight`, and number keys 1–9/0 (hand index, shown by each card's `Hotkey` label) to toggle selection (selected card parks at `_selectedPosition`, the rest of the hand closes the gap, `CardTargetingArrow` draws a Bézier of chevrons to the cursor). It owns no game rules: `PlayerActionController` polls `SelectedCard` / `FocusedCard` — move range when nothing is focused, launch zone when a card is hovered or dragged, targeting when one is selected — and plays on a left press or release over a valid cell, cancels on right click or a left press elsewhere. Cost is displayed but not yet spent — there is no energy yet.

### Currency
`CurrencyAsset` (SO) wraps the `Currency` enum plus icon / display name / TMP sprite tag. `GameData.currencies` is keyed by the **enum**, so renaming or reordering `Currency` members invalidates existing saves. Currency gains can auto-feed tracked values via `CurrencyAsset.trackedValuesWithCurrencyGained`.

### Tracked values
`TrackedValueType` (enum) → `GameData.trackedValues`, with `GameData.OnTrackedValueChanged` as the broadcast hook. New metrics = new `TrackedValueType` entries (they are auto-seeded in `ResetGameData`).

### Pooling
**Pool only high-churn UI; everything else uses `Instantiate` / `Destroy` until the profiler says otherwise.** Pooled today, and nothing else: card views, card trails, floating text, flying particles. Entities, entity HUDs and their status-effect icons, projectiles and every VFX are plain instances — in a turn-based game their spawn cost is invisible, while every pooled type needs its state fully reset on reuse, which is discipline we only pay for where churn justifies it. `Entity.Despawn()` runs every module's `Cleanup` and then `Destroy`s the GameObject; an entity destroyed by a scene unload skips `Cleanup`, so a module that owns something outside its own hierarchy (the HUD lives on `RunCanvas`) must also release it in `OnDestroy`. A short-lived VFX is `Destroy(Instantiate(prefab, ...).gameObject, lifetime)`, with the lifetime serialized beside the prefab reference (`EntityHealthModule._deathVFXLifetime`, `Projectile.m_vfxLifetime`). Instances spawned without a parent land in the active scene, which is `CombatScene` during a fight, so they die with it.

Where pooling is used it is direct Lean Pool: `LeanPool.Spawn(prefab, ...)` / `LeanPool.Despawn(this)`. **No pool setup is needed** — an unknown prefab gets a `LeanGameObjectPool` created on demand in the active scene (our fork used to log an error there; it no longer does). Hand-placed pools (Card and CardTrail under `CombatCanvas`'s `_Pools`) exist only to choose where despawned clones are parented. Never enable **Recycle** on a pool whose clones are owned by something (cards): at capacity it steals the oldest *live* clone from its owner. A pooled object must reset all of its state in its spawn/init path or `IPoolable.OnDespawn` — kill tweens, cancel async loops, clear callbacks (`UIFlyingParticle` cancels its burst loop this way). Never parent a pooled clone under a non-pooled object: destroying the parent destroys the clone behind its pool's back. UI spawners (`FloatingTextManager`, `FlyingParticleManager`) expose a parent Transform field because UI clones must land under a Canvas to render.

### Audio
`SoundManager` (pooled `AudioPlayer`s, dedicated music/ambient players, per-sound throttling) plays entries from a `SoundLibrary` by the `SoundKeys` enum. **`Team Square/SoundLibrary/Scripts/SoundKeys.cs` is generated** — an Odin `[Button]` on `SoundLibrary` rewrites that exact file from the library's entries. Never hand-edit it; edit the library and regenerate.

## Conventions

- Serialized private fields use `_camelCase`; method parameters are often `_camelCase`; public SO/data fields are plain `camelCase`.
- Logging goes through the `DrowsyLogger` extension methods on `UnityEngine.Object`: `this.Log(msg)`, `this.LogWarning(msg)`, `this.LogError(msg)` — colored and prefixed with the object name. Prefer these over raw `Debug.Log` in new MonoBehaviours.
- Inspector-visible dictionaries/sets use `Utils.SerializableDictionary` / `SerializableHashSet`.
- Tweening is DOTween; store tweens and `Kill()` them before restarting (see `UIContainer`, `CustomButton`).
- Large numbers are displayed via `NumberFormatter.FormatValue` / `value.ToSmartString()`. Currency amounts are `double` (or `ulong` in `Cost`).
- Functions and variable names should make what they're about obvious
- **Gameplay randomness goes through `RunRandom.GetStream(RandomChannel.X)`, never `UnityEngine.Random` or `CusRandom`** — seed sharing and bug reproduction depend on it. Pick the channel that matches the system you are in, and add a channel rather than borrowing an unrelated one. `CusRandom` / `UnityEngine.Random` stay fine for purely cosmetic effects (VFX, audio pitch, floating text).
- **Domain reload is disabled when entering play mode**, so statics are never reset automatically. Every mutable `static` field must be cleared by a static method marked `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]`, which runs before any scene loads on each play. The exception is a `UnityEngine.Object` static that is only ever read through `if (x == null)`: Unity's overloaded `==` reports a destroyed object as null, so it self-heals (this is why MyBox `Singleton<T>` and the cached `Material` statics survive). `??`, `is null` and `?.` do *not* — they are plain C# checks and see a stale reference. Assets from `Resources.Load` are never destroyed, so they self-heal in no case at all and always need the explicit reset.
- Never write any comment
- Input goes through the new Input System: the project is `activeInputHandler: 1` (new input only), so legacy `Input.*` calls compile fine and throw at runtime — never reintroduce them.
- Odin inspector-customization attributes are forbidden — `[ShowIf]`, `[InlineEditor]`, `[TitleGroup]` and every other group, and anything else that changes how the inspector is laid out or displayed — because inspector customization is handled elsewhere since the tool's latest version. Remove them when touching a file. Odin `[Button]` is allowed for editor-invocable actions, debug helpers included.
- Avoid GetComponent in awake as it hides the responsability of getting the component. Always serialize what need to be there and use [RequireComponent], [Required] and Reset() to help with getting it

## Known hazards

- A **baked NavMesh stored inside a scene** forces that whole scene file to binary, because `NavMeshData` prefers binary serialization — even with `m_SerializationMode: 2` (ForceText). Bake through the editor, or, when baking from script, follow it with `AssetDatabase.CreateAsset(surface.navMeshData, "Assets/.../<SceneName>/NavMesh-<object>.asset")` so the data lives in its own asset and the scene stays diffable (this is how `MainScene/NavMesh-Ground.asset` and `MenuScene/NavMesh-HubGround.asset` exist).

- `GameData.SpendCurrency` indexes `currencies[currency]` after an `||` with `noCurrencyRequired`, so enabling that cheat for a currency that was never added throws. `ResetCurrencies()` seeds every key from `GameAssets`.
- Every runtime file that touches `UnityEditor` is wrapped in `#if UNITY_EDITOR` (verified). Keep it that way — an unguarded `using UnityEditor;` compiles fine in the editor and only fails at player-build time.
- To verify compilation without the editor: Assembly-CSharp can be compiled headlessly with Unity's Roslyn (`dotnet "<UnityRoot>/Editor/Data/DotNetSdkRoslyn/csc.dll" @rsp`), feeding it the `HintPath` references and `DefineConstants` from the generated `Assembly-CSharp.csproj` plus `Library/ScriptAssemblies/*.dll` (excluding `Assembly-CSharp*.dll`). Useful when the editor holds the project lock.
